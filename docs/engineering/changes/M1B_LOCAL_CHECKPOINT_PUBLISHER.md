# M1b — local controlled checkpoint publication registry (experimental)

## Current state and goal

PRs #40–#42 implemented a transactional **review** history, signed
checkpoints and an **offline** witness transcript. None manages a live
checkpoint publisher, an independently trusted current head, operator
authentication, signing-key custody, or global anti-equivocation.

Add a narrow local SQLite **publication** registry, in a **separate file**
from the review SQLite database. The publication registry accepts only
externally pre-signed requests naming configured operator keys, checks
both reviewer-checkpoint/witness signatures, serializes one publisher
per packet/sequence, stores metadata and a durable local head, and
rejects missing/incorrect predecessor, duplicate or conflicting writes.
Do **not** present local durability as an independent, live authority.

## Acceptance criteria

- Creation requires a new explicit absolute path; opening an existing
  database never resets its stored version. No overwrite of an existing
  path on `create=True`.
- Accept a domain-separated operator-signed request only if its operator
  key appears in a separately configured publishing role. No signer
  private keys are handled or generated by the production module.
- Verify existing checkpoint signatures, witness signatures and exact
  source packet + purpose binding. Reject signer role overlap, unsigned
  handoffs, changed/missing keys, malformed commands and altered
  contents. Rotation needs signatures from both witness keys.
- SQLite `BEGIN IMMEDIATE` ensures one winner for two competing
  writers at the same expected sequence and head. Event and head
  commit atomically, with interruption rollback.
- Reopening from disk verifies the entire stored signed publication
  chain; stale, truncated, altered records or mismatched head fail.
  Signed revision/head and issue date cannot regress.
- Preserve a documented and tested counterexample: restoring an old,
  internally coherent **publisher** database cannot be detected by the
  publisher alone. The same signer/role keys can sign a fork if operator
  governance is compromised. An independent published head is still
  required.
- Receipts are identifier-minimized and always deny ingestion and
  forecasting; no new HTTP route, source ingestion, real identity
  provider, protected key store or live witness network.
- Full repo tests, Ruff, catalog, atlas, evidence and capability guards
  must pass on an exact clean PR HEAD under the prior owner-authorized
  temporary local QA policy.

## Threat model, compatibility and rollback

A local SQLite file, configured public-key map and a domain-separated
operator signature are not an externally trusted, authenticated service.
The caller and local administrator control storage, clock, key policy and
fencing. Rollback, cross-machine forks, key theft and hidden equivocation
still require independent administration, protected keys, witnessed
monotonic publication and audited response policies. The feature can be
reverted without migrating review-registry schema, source readers or API
request contracts. A production authority requires a separate design
and security review, including trusted signer identity and revocation.
